# Known issues and limits

Behaviour that is intentional but surprising, and limits of the prototype. Each entry says where it lives. The
converter's own list (conversion, mapping, Claude, app) still applies to every import:
[converter/KNOWN_ISSUES.md](converter/KNOWN_ISSUES.md).

## Data and imports

| # | Issue | Effect | Where |
|---|---|---|---|
| 1 | **Two databases.** Import jobs, templates and drafts are in `data/converter.db` (SQLite); records are in PostgreSQL. An import is linked by `job_id` (the number on the Imports page). | If `data/` is deleted or a second app install uses the same PostgreSQL, job numbers start again at 1 and the "Open the import" link of old records can open the wrong job (the records themselves are unaffected: they point to their PostgreSQL import). Keep one `data/` per database. | `app.start_import`, `imports.job_id` |
| 2 | **A record field can be added, not renamed or retyped automatically.** Adding a field adds its column on the next start. A renamed field gets a new, empty column (the old one stays); a retyped field keeps its old column type and the app warns in the sidebar. | Retyping a field with data is a decision for a person: convert the column by hand (`ALTER TABLE records ALTER COLUMN …`) or add a new field. An import into a mismatched column can fail. One exception, decided for 1.2.0: a date-and-time field whose format has no time (the last visit) has its column converted to a date on start (#28). | `db.Database.setup` |
| 3 | **An import is stored in one transaction, and the whole file is held in memory** (as in the converter). | 20,000 rows take a few seconds; files of millions of rows need more memory and time. | `importer.RecordSink.save` |
| 4 | **No duplicate check across imports.** The same customer in two files is two records; the same file imported twice for a business is only warned about. | Tag exports merge numbers, so the main system receives each number once; counts of records include repeats. | `store.same_file_imports` |
| 5 | **Re-running a completed import needs its records deleted first**, which also takes them out of tags. | Tags must be filled again from the new records. | `app.can_rerun`, `store.delete_import` |
| 6 | **Records can only be deleted per import.** There is no "delete this record". | Delete the import's records and re-import, or leave the record and keep it out of tags. | — |
| 7 | **Merchants and locations are copies of the main app's** (1.6.0), loaded every hour from its ClickHouse, or when someone uploads a new export on the Merchants page. | A merchant or location just added in the main app can't be imported for until the next load: on the Merchants page, *Load from the main app now*, or upload a new export. | `merchants.MerchantRefresher`, `store.load_merchants` |
| 8 | **The converter's command line (`converter.cli convert`) doesn't store records**: it has no business or service, and runs the converter's import (number history, converted file). | Import through the web app. | `converter/cli.py` |
| 23 | **"Kept as written" means as the converter's reader reads the cell**: spaces around a value are trimmed, and an Excel date cell is text like `1990-05-06 00:00:00`. | Search *Column: …* for the trimmed value. | `converter.reader`, `importer.build_records` |
| 24 | **A record's numbers are in the order of the phone field's columns**, which the converter's rules put mobile columns first in (Mobile before Phone), not always the file's column order. | Only the order shown on the record; every number is stored and exported. | `converter.heuristics` step 2, `importer.build_records` |
| 37 | **Each import runs in its own worker process** (1.5.0, `IMPORT_WORKERS`, default 5): it takes about 1.5 s to start, and holds about 0.4 GB of memory per 20,000 rows (1 GB per 100,000) until it ends. Five imports run truly at the same time only with five free CPU cores; with fewer they share them. | On a small server lower `IMPORT_WORKERS`. A worker process stopped by the system (out of memory) fails only its own import, which says so; re-run it. | `records/runner.py` |
| 38 | **Stopping or updating the server stops its imports** (1.5.0): those running or waiting show *Interrupted*, with nothing stored. Before, the server first finished them all, with the pages already gone; under Docker it was cut off after 10 seconds anyway. | *Re-run* them. | `runner.ProcessImportRunner._run` |
| 39 | **On Windows, a worker process doesn't notice that its server was killed** (ended by force, not stopped): it finishes its import, which the next start had marked *Interrupted* and then shows *Completed*. On macOS and Linux it stops within a second. | Don't re-run an interrupted import on Windows until it has stayed interrupted for a few minutes. | `runner._stop_with_server` |
| 40 | **One location per import** (1.6.0). A corporate account's export that mixes its locations (a *Store* or *Location* column) can't be imported in one go. | All its rows would get the one location chosen: split the file by location first. Planned: map the column, each of its values to a location (a person confirms; Claude can suggest). | `store.create_import` |
| 41 | **Imports and records from before 1.6.0 have no location.** A business typed in by hand whose ID is a main app merchant ID becomes that merchant (renamed); the others show as *no longer in the main app* after the first load (their records stay and are found by merchant). A typed `0063` is not merchant 63. | A find by location never finds them, and they can be re-run only when their merchant has a single location in the main app (it is taken): start clean with `scripts/reset_records.py --yes` (test data only), or import the files again for their locations. | `db.Database.setup`, `app.can_rerun` |
| 42 | **Records keep the merchant and location they were imported for.** A location the main app moves to another merchant keeps its old records under the old merchant (and in that merchant's tags). | Rare; finds by the new merchant don't include them: import the file again for the new merchant. | `store.load_merchants` |
| 53 | **Consent stored before 1.8.0 was read without consent settings** (file-converter 0.23.0 came in 1.8.0): a no in a mapped consent column (an *Email Opt In* = N) was stored as false, opted out, and a column of opt-outs (*Unsubscribed*) couldn't be read as one. | Records imported before 1.8.0 with consent mapped keep what was read then. To read them again with settings: open the import, *Delete this import's records*, then *Re-run this import*, which first asks what each consent column records. | `records_schema.yaml` (`opt_out_choice`), `app._ask_rerun_consent` |
| 9 | **The converter's Number history page isn't shown**, and `NUMBER_RECORD_DAYS` has no effect: the runner's sink replaces the number recording. | Use Find (Phone, then the record's import) instead. | `app.get_runner` |

## Find

| # | Issue | Effect | Where |
|---|---|---|---|
| 43 | **The Locations picker lists only the locations of corporate accounts** (merchants with several), all of them whichever merchants are picked (1.6.0). | A one-location merchant is found by picking the merchant. A location picked together with another merchant finds nothing: a request needs both. | `ui.page_find` |
| 10 | **FileMaker syntax with differences**: `@` and `#` are ordinary characters (so emails and "Apt #4" can be typed), `!` (duplicates), `?` (invalid dates) and `~` aren't supported and say so; month/day without a year (`10/9`) means "any year". | Expected by design; listed under *How to search*. | `criteria.py` |
| 11 | **Two-digit numbers after a month are days, not years**: `10/25` is October 25 in any year, not October 2025 (`10/2025`). | Type the year with four digits. | `criteria.date_token` |
| 12 | **`Column: …` compares text**, as written in the file: `>=100` compares alphabetically ("50" > "100"). | Map the column to a typed field to search it by value. | `criteria._condition` ("column") |
| 25 | **Upper/lower case of accented letters depends on the database's locale.** The app creates its database with ICU rules (Å = å). A database made by hand with the C locale (Homebrew's default) only folds A-Z: finds then add an explicit collation (correct; the sidebar says so), which keeps text searches from using their index. | On a large database made by hand, re-create it with `CREATE DATABASE … LOCALE_PROVIDER icu ICU_LOCALE 'und' …` (or let the app create it) and restore a backup. | `db.ensure_database`, `db._case_collation`, `criteria.text_condition` |
| 14 | **Text searches need `pg_trgm`** to be fast on large databases. Without it (a server that doesn't allow the extension) they still work, slower; the sidebar says so. Indexes are used by text, number and date fields, the Date and First / Last name (before 1.3.0 no find used one). Phone, Record created, Full name, a file's columns (*Column: …*), Tag, File name, Import # and Consent read every record: about 0.1–0.4 s per find at 300,000 records, more for larger databases. | Ask for the extension on a shared server. | `db.Database.setup` |
| 15 | **Selecting rows works per page** of the found-set table; *Omit selected* omits the selected rows of the page shown. | Omit page by page, or narrow the find. | `ui._found_set` |
| 16 | **Dates and times are as written in the client's time zone** (converted only when the file gave a zone, as in the converter); *Record created* uses `APP_TIMEZONE`. A day of the week (`fri`) is that of the day as stored, on the same clocks. | Comparing activity dates across businesses in different zones compares local clock times. | `criteria`, `importer.typed_value` |

| # | Issue | Effect | Where |

## Sending to the main app

| # | Issue | Effect | Where |
|---|---|---|---|
| 45 | **The main app doesn't load the files by itself yet** (1.7.0). Since 2026-10-15 nothing picks up files from its bucket; an import lands when its dashboard runs `imports.ingest`. | The files wait in `data/customer-records/` and `data/customer-records-tags/` until the main app loads those folders (docs/BUCKET_FILES.md has tables and queries for it). *Sent* means in the bucket, not in ClickHouse. | the main app |
| 46 | **A deletion reaches the records, not what the main app made of them.** Deleting an import's records sends a deletion file; the main app's audiences fold only adds, so the numbers and dates it took from the import stay there unless rebuilt. | Delete records only to fix a mapping, and expect the main app's segments to keep the old activity until its side handles deletions. | `bucket.write_delete_file`, the main app |
| 47 | **A tag's snapshot is built when it is sent, not when it was exported** (one waits at a time per tag). | If the tag changes between the export and the send (seconds, or longer while the bucket can't be reached), the main app gets the newer contents, not the downloaded file's. | `bucket.write_tag_file`, `store.queue_tag_send` |
| 48 | **Imports completed before the bucket was set up are all sent once it is**, and a big import is one file in one request (R2 takes up to 5 GB per file). | Setting up the bucket on a full database sends everything, one file at a time. | `BucketSender.queue_completed_imports` |
| 49 | **`reset_records.py` doesn't touch what was sent.** It empties the queue and history here; the files stay in the bucket and in the main app. New imports get new UUIDs, so nothing clashes. | The main app keeps the test data sent before a reset until it is removed there; the script says how many files went. | `scripts/reset_records.py` |
| 51 | **One app server per database sends.** A sender takes over, at its start, every send another process left half done (meant for a server that stopped during a send). | Two app servers on one database would each take over the other's sends at their start: the same file sent twice (harmless: same contents, the later wins). | `BucketSender.run_once` |
| 52 | **A deletion can arrive for an import file that never did.** An upload that failed or was cut off can still have reached the bucket, so deleting its records sends the deletion anyway, after the import's send is given up. | The main app may load a deletion file whose keys match nothing (no effect with `FINAL`). | `store.queue_import_deletion` |
| 50 | **Only merchants of the main app are sent** (an ID that is a number). Businesses typed in by hand before 1.6.0 aren't, and their tags can't be. | Their imports show nothing under *Main app*; reset or re-import them for main app merchants. | `BucketSender.queue_completed_imports`, `store.queue_tag_send` |
